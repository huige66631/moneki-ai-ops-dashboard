# 第二关：AI 数据问答实施计划

## 1. 目标和边界

本阶段在第一关看板中加入一个自然语言对话框。运营人员可以询问门店品类营业额、指定商品营业额和客单价趋势。系统必须使用真实 SQLite 查询结果回答，不能让模型直接阅读 CSV 或猜数字。

本阶段不实现多轮对话、流式输出、自动生成图表、部署和第三关增强项。可以为后续多轮对话保留清晰的会话边界，但不要提前引入复杂的消息存储。

## 2. 必须满足的验收标准

1. 问“哪个品类的门店营业额最高？”时，系统必须 JOIN `stores` 表，并返回门店品类、真实净营业额和查询范围。
2. 问“牛肉poke 六月卖了多少钱？”时，系统必须 JOIN `products` 表，并返回真实商品名称、2026 年 6 月的净营业额和订单数。
3. 问“客单价最近是涨了还是跌了？”时，系统必须返回两个可复核的 7 天窗口、两个客单价和变化方向。
4. 回答中的每一个业务数字都必须能在工具结果和第一关 API 的同一统计口径下复算。
5. 询问成本、利润、库存或数据中不存在的商品时，系统必须明确拒答或请求澄清，不得生成数字。
6. 没有 API key 时，Mock 提供商仍必须执行真实工具函数。Mock 不能直接写死示例答案中的金额。
7. API key 只从服务端环境变量读取，不进入浏览器、Git、日志、响应或错误信息。

## 3. 推荐架构

沿用第一关的后端分层，并增加以下目录：

```text
backend/app/
  ai/
    __init__.py
    contracts.py          # 提供商、工具调用和回答状态模型
    orchestrator.py       # 校验、调用、结果验证、回答渲染
    prompts.py            # 系统提示词和工具描述
    providers/
      __init__.py
      base.py             # Provider 协议
      mock.py             # 无密钥开发和测试
      deepseek.py         # 可选真实模型适配器
    tools/
      __init__.py
      dashboard_queries.py # 三个白名单查询工具
      resolver.py          # 商品和日期解析
frontend/src/
  features/assistant/
    AssistantPanel.tsx
    assistantApi.ts
    assistantTypes.ts
```

模型调用适配器只负责把用户问题和工具定义发送给模型，并返回结构化工具选择。编排器负责工具白名单、参数校验、数据库执行和最终回答。这样后续更换模型不会改变查询口径。

## 4. 提供商设计

### Mock 提供商

Mock 是默认模式，适用于本地开发、自动化测试和没有 API key 的演示。它模拟模型的“选择工具”行为，不模拟数据库结果。

Mock 的最小能力包括：

- 根据固定的意图规则识别三个作业示例问题及其同义表达。
- 从问题中解析月份、日期范围和商品名称。
- 返回和真实模型相同结构的 `ToolCallPlan`。
- 无法识别时返回 `unsupported` 或 `needs_clarification`。

Mock 规则只返回工具名称和参数。它不能包含 `revenue`、`order_count` 或 `average_order_value` 等查询结果字段。

### DeepSeek 提供商

DeepSeek 提供商通过服务端 HTTP 客户端调用模型的工具调用接口。具体模型名、基础 URL 和超时由环境变量配置；不要把供应商 SDK 或模型名散落在业务代码中。

建议环境变量：

```text
MONEKI_AI_PROVIDER=mock
MONEKI_AI_API_KEY=
MONEKI_AI_BASE_URL=
MONEKI_AI_MODEL=
MONEKI_AI_TIMEOUT_SECONDS=20
```

真实提供商出现超时、非结构化回复、未知工具名或无效参数时，编排器应返回可读的 `error`，不能回退到模型自由回答。测试环境强制使用 Mock 或 fake provider，不访问网络。

## 5. 意图和日期解析

第一版只允许三个意图：

```text
category_store_revenue
product_revenue
recent_average_order_value
```

日期解析优先级如下：

1. 问题中明确的日期或月份。
2. 当前看板 `context` 日期范围。
3. 数据库中的最小和最大有效日期。

“六月”在当前数据集解释为 `2026-06-01` 到 `2026-06-30`。如果未来数据跨年，解析器必须根据数据范围或明确年份请求澄清，不能默认使用当前系统年份。

商品名称解析要先在 `products` 表中查找规范化名称，再得到 `product_id`。规范化只处理大小写、空白、全角半角和常见中英文标点，不做模糊的“最相似商品”自动选择。多个匹配或没有匹配时，返回候选或澄清问题。

## 6. 查询工具实现要求

- 所有查询使用参数化 SQL。
- 查询函数接收已经通过 Pydantic 校验的日期、ID 和枚举值。
- 不允许传入 SQL、表名、列名或 SQL 片段。
- 金额继续以整数分从 SQLite 读取，在服务层转成 `Decimal` 再序列化。
- 三个工具必须复用第一关的有效记录口径：有效日期、有效订单号、有效金额、去重记录，保留负金额。
- `get_category_store_revenue` 必须明确使用 `stores.category`，避免与商品类别混淆。
- `get_product_revenue` 必须返回商品 JOIN 结果，未匹配商品不能被替换成另一个商品。
- `get_recent_average_order_value` 必须返回两个窗口的原始汇总值，让页面和测试可以复算方向。

## 7. 回答生成和可信度保护

采用“模型选工具，后端生成数字回答”的最小可交付版本方案：

1. 提供商返回工具调用计划。
2. 编排器验证工具调用计划。
3. 查询工具执行真实数据库查询。
4. 编排器验证工具结果的 Pydantic 结构和数值范围。
5. 确定性的回答渲染器把工具结果转成中文回答。
6. API 同时返回 `tool_call` 和 `evidence`，供页面显示查询依据。

这个方案仍然保留真实的模型工具调用链路，同时避免模型在最后一步改写数字。以后需要更自然的长回答时，可以让模型只润色已经插入的证据，但必须保留数字一致性校验。

回答规则：

- `answered` 必须包含结论、日期范围、核心数字和证据摘要。
- `unsupported` 只说明当前数据能力，不包含猜测数字。
- `needs_clarification` 说明缺少的商品、日期或窗口信息。
- `error` 不暴露供应商响应、密钥、堆栈或完整内部提示词。

## 8. 后端实施步骤

### 步骤 1：建立契约和工具测试

- 添加 `contracts.py` 中的请求、响应、工具调用和证据模型。
- 添加三个查询工具及商品解析器。
- 使用现有 `backend/tests/conftest.py` 的 SQLite fixture 扩展测试数据。
- 测试 JOIN、负金额、未匹配 ID、日期边界、7 天窗口和并列结果。

完成标准：不调用任何模型，三个工具都能返回可复核的结构化真实数据。

### 步骤 2：实现提供商和编排器

- 定义 `Provider` 协议和 Mock 提供商。
- 实现 DeepSeek 可选适配器，默认不启用网络调用。
- 实现单次工具调用编排器、白名单校验、错误映射和确定性回答渲染。
- 添加 `POST /api/v1/assistant/ask`，上下文日期沿用第一关筛选范围。

完成标准：用 fake provider 测试“计划 -> 工具 -> 证据 -> 回答”完整链路；回答数字严格等于工具结果。

### 步骤 3：接入看板对话框

- 在第一关看板中新增 `AssistantPanel`，保留当前日期范围上下文。
- 提供输入框、提交按钮、三个示例问题、加载状态、错误状态和空状态。
- 展示回答、查询范围和可展开的证据摘要。
- 发送新问题时保留看板数据，不阻塞日期筛选。
- 不实现伪造的打字机效果，不在浏览器端保存 API key。

完成标准：三个作业示例可以在页面完成提问；切换日期范围后，不带明确日期的问题使用新范围。

### 步骤 4：验证真实数字和文档

- 增加一组契约测试，先调用第一关 dashboard 服务，再调用 AI 工具，对比相同日期范围下的金额和订单数。
- 增加 unsupported、clarification、provider timeout、未知工具和无商品匹配测试。
- 更新 README 的第二关运行方式和 Mock 模式说明。
- 创建 `AI_USAGE.md`，记录真实使用过的 AI 工具、提示词、AI 出错案例、发现方式和修复方式。
- 手动录制三个示例问题的 1 到 3 分钟演示素材。

完成标准：评审者可以从 API 响应、证据摘要和测试用例追溯每个回答数字。

## 9. 测试清单

### 查询工具测试

- 门店品类营业额确实 JOIN `stores`，并按营业额排序。
- 商品营业额确实 JOIN `products`，六月边界包含 6 月 1 日和 6 月 30 日。
- 负金额会影响净营业额，但无效金额不会进入结果。
- 未匹配商品返回回退身份，不会被归入其他商品。
- 最近 7 天和之前 7 天的客单价方向可由结果独立计算。
- 不足 14 天或无订单时返回 `insufficient_data`。

### 编排器和接口测试

- Mock provider 的工具计划不包含数字结果。
- 未知工具名被拒绝。
- 工具参数越界、日期反转和超长问题被拒绝。
- 工具结果中的数字进入回答和 `evidence` 时保持一致。
- unsupported 问题不执行查询工具。
- provider 超时返回 HTTP 503，且不泄露内部信息。
- 真实 provider 在测试中不会发出网络请求。

### 前端验收

- 三个示例问题能显示回答和证据。
- 加载时输入和按钮状态清晰，旧看板数据不消失。
- 接口错误和无法回答的问题使用不同的可读状态。
- 证据摘要显示查询日期、商品或门店品类和关键数字。
- 窄屏下输入框、按钮和回答不溢出。

## 10. Git 提交安排

第二关新增三次提交即可，连同第一关已有历史不会显得刻意拆分：

```text
docs: define ai data qa contract
feat(ai): add verified query tools and provider orchestration
feat(ai): add dashboard assistant and numeric verification
```

第一笔只提交本目录的计划和契约。第二笔提交查询工具、Mock/DeepSeek 适配器、编排器和后端测试，不加入前端聊天框。第三笔提交 API 接入、对话框、契约测试、README 和 `AI_USAGE.md`。如果真实开发中出现可复现缺陷，再增加对应的 `fix(ai): ...`，不要创建没有内容的占位提交。

## 11. 给执行 AI 的约束

- 先阅读本目录全部文档和第一关实现，再开始改代码。
- 一次完成一个实施步骤，每一步都运行相关测试。
- 不要读取或上传外部凭据，不要把 API key 写入文件或终端命令。
- 不要让模型生成 SQL，不要执行模型返回的任意函数或 URL。
- 不要为了通过演示而把真实金额写进 Mock 回答。
- 如果真实模型协议和当前适配器不兼容，保留 Mock 链路可运行，并在 README 说明限制。
- 实现结束时报告修改文件、测试命令、测试结果、实际 provider 模式、未完成内容和下一次提交信息。
